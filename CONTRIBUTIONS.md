# Contributing to `modules/`

The `modules/` directory ships the canonical GNU Make modules published for downstream consumers. This guide translates the enforcement rules from [.github/instructions/makefile-consistency.instructions.md](.github/instructions/makefile-consistency.instructions.md) into a practical workflow. The canonical command and compatibility reference is [README.md — Aggregate and Module-Scoped Targets](README.md#aggregate-and-module-scoped-targets).

The repository includes `examples/` as module-by-module MVP projects. Keep
those examples simple and standalone so users can copy one folder and get
started quickly.

## 1. Mental Model

The tree below is the required scaffold, not an inventory or claim that every
existing module already conforms; audit existing modules before reporting
compliance.

```
modules/
  ├── Makefile                 (root: shared variables, dispatch, helpers)
  ├── manifest.txt             (lists every published file; fetch reads this)
  ├── core/                    (shared infrastructure, not a consumer module)
  └── <module>/                (one reusable consumer module)
      ├── Makefile             (entry point: includes root and registers targets)
      ├── prerequisites.mk     (prerequisite configuration and private support rules)
      ├── targets.mk           (public target definitions and recipes)
      ├── <helper>.mk          (optional non-target helper fragment)
      └── <helper>.sh          (optional module-owned helper script)
```

- **Root Makefile** (`modules/Makefile`): defines environment variables (`MF_*`) that every module consumes.
- **Manifest** (`modules/manifest.txt`): one path per line (relative to `modules/`) for every file that `fetch` may download. The `fetch` script always pulls the root `Makefile` plus every line that starts with the requested module's name.
- **Module Makefile** (`modules/<module>/Makefile`): includes the root immediately after its header, then the guard and module fragments; it registers the module's public targets.
- **Required fragments** (`modules/<module>/prerequisites.mk` and `targets.mk`): the former holds prerequisite configuration plus private prerequisite/support rules and their recipes; the latter owns public module target definitions and recipes. Both follow the header + guard convention and must *not* include the root.
- **Optional helper fragments** (`modules/<module>/*.mk`): provide variables or helper functions only; they must *not* include the root directly or define targets.
- **Module scripts** (`modules/<module>/*.sh`): optional module-owned helpers (for example config path discovery). Keep them module-local; avoid module-specific logic in core.
- **Core scripts** (`modules/core/*.sh`): shared helpers are allowed only when they are module-agnostic (for example reusable path handling and cleanup guardrails).

### Standard module interface

Every consumer module must provide public `clean`, `install`, and `help`
targets, including an explicit no-op with a useful message when an operation
does not apply. Register these targets alongside any other public targets in
the module entry Makefile. Use `clean::` and `install::` so contributions from
imported modules compose in aggregate mode. `make help` is top-level help;
`make <module> help` is generated from that module's registration. Help must
have no prerequisites or side effects. `clean` must be safe, repeatable, remove
only module-owned generated artifacts, and avoid discovery/cache prerequisites;
`install` prepares the module's dependencies. Document detailed behavior and
options in the README.

A consumer's normal include/bootstrap pattern may fetch missing cached module
files before Make executes help; the help target itself must not initiate that
fetch or any other side effect.

The shared registry rejects missing `clean`, `install`, or `help` targets,
duplicate public registrations, and the retired `echopath` target. Keep every
public target in the registration list exactly once and omit private
prerequisites.

### Shared workflow vocabulary

The required module interface remains `help`, `install`, and `clean`. The
workflow targets below are shared conventions, not additional requirements:
register a target only when the module performs that operation. Keep their
meaning consistent across modules:

- `check`: static validation that does not change source, configuration, or
  lockfiles and does not run dependency install/update commands or tests. Tools
  may write local build/cache files or fetch already-locked dependencies.
- `test`: execute tests. Typechecking by itself belongs under `check`.
- `build`: produce the normal local build; use a development/debug profile by
  default when the toolchain has build profiles.
- `release`: produce an optimized/production build when distinct. It must not
  publish or deploy the result.

Use double-colon rules for aggregate contributions. When a project has only
one meaningful build mode, `build` may map to it and `release` may alias it or
remain unavailable; do not invent a debug mode. The canonical definitions and
the optional follow-up vocabulary are in [README.md](README.md#shared-workflow-vocabulary).
The current TypeScript module's type-only check is `check`, not `test`.

### Optional vocabulary for a follow-up phase

The candidate names and their safety guidance are maintained in the canonical
[README vocabulary section](README.md#optional-vocabulary-for-a-follow-up-phase).
They are not required targets and must not be registered as no-op recipes.

Document mutation and external effects. In particular, keep formatting and
dependency updates explicit, and never make publishing, deployment, service
teardown, or database reset an implicit consequence of a build or clean.

Keep prerequisite configuration and private prerequisite/support rules (and
their recipes) in `prerequisites.mk`; keep public module target declarations
and recipes in `targets.mk`. The entry Makefile includes the root and its guard
first, then includes `prerequisites.mk` followed by `targets.mk`. Do not put
public target rules in `prerequisites.mk` or target rules in optional helper
fragments. If there are no extra prerequisites, keep the required
`prerequisites.mk` with its normal header and guard; it may be otherwise empty.
List both required files and any additional module files in
`modules/manifest.txt`.

### Aggregate and module-scoped invocation

Consumers can use either of these forms:

- `make <target>` is aggregate mode. It runs the target contribution from
  every imported module that defines it, plus any shared root contribution,
  preserving normal GNU Make import order.
- `make <module> <target>` is scoped mode. It runs only the named imported
  module's target. The module must be explicitly included by the consumer;
  a cached but unreferenced module is not eligible for dispatch.

For example, when a consumer imports modules that both expose `build`:

```console
make build              # all imported build contributions, in import order
make rust build         # Rust build only
make typescript build   # TypeScript build only
```

Every public module target must be available under its module namespace using
the `make <module> <target>` pattern. The module name is the directory name
under `modules/`; do not invent aliases or encode the namespace into the
target name. For example, `modules/phpunit/Makefile` exposes its `test` target
as `make phpunit test`.

Register public targets in the module entry Makefile after the shared root
include and guard. The root derives the namespace from the entry file path;
keep the list current when adding, renaming, or removing public targets. Always
register `clean`, `install`, and `help` alongside any module-specific public
targets, and omit private prerequisites. For example:

```make
MF_CURRENT_MODULE_ENTRY := $(lastword $(filter %/modules/<module>/Makefile,$(MAKEFILE_LIST)))
$(eval $(call mf_register_module,$(MF_CURRENT_MODULE_ENTRY),clean install help test coverage coverage-open))
```

Keep all public module target declarations and recipes in `targets.mk`; it may
depend on private prerequisite/support rules from `prerequisites.mk`. Use GNU
Make's double-colon rule (`target::`) for targets that contribute to aggregate
`make <target>` behavior alongside other modules. Scoped invocation selects
only the named module's registered implementation.

Preserve the PHPUnit-specific targets `test`, `coverage`, `coverage-open`, and
`install-phpunit-binary`; register them alongside the required `clean`,
`install`, and `help` targets. The module uses the consuming
project's Composer-installed `vendor/bin/phpunit` by default; the standalone
PHAR installer is opt-in and does not replace that executable. Set `BROWSER`
when the default browser opener is not suitable; coverage output paths are
discovered from `phpunit.xml` and fall back to `coverage/`.

Codeception and PHPUnit discover coverage paths with module-local scripts and
persist resolved values to `.makefiles/cache/`. Path-dependent targets such as
`coverage` and `coverage-open` should depend on the same cache file to
guarantee consistent behavior within a run. Keep module `clean` targets
independent from cache-file prerequisites so base cleanup can remove generated
folders without recreating `.makefiles/` mid-run.

Apply the same dispatch and registration rules to Codeception, PHPUnit,
TypeScript, and Rust. Keep scoped targets explicit (`make vitest test`,
`make vitest coverage`, `make typescript check`, `make typescript build`,
`make rust build`, `make rust check`, `make rust release`, `make rust test`,
`make rust clippy`, `make rust fmt`) and register each new public target in the
module entry Makefile when it is added.
The Rust module resolves its cargo target directory from `cargo metadata`, so
`CARGO_TARGET_DIR` and `.cargo/config.toml` overrides are honored by `clean`.

The exact two-goal form is reserved for scoped dispatch. Unknown modules and
targets fail before recipes run, print an actionable message to stderr, and
return status 2. One-goal aggregate calls and calls with more than two goals
retain their existing GNU Make interpretation. A consumer that must retain
the old two-goal GNU Make interpretation can set `MF_LEGACY_GOALS=1`. See the
[canonical README build guidance](README.md#aggregate-and-module-scoped-targets)
for the full invocation contract and examples.

## 2. Required Header + Guard
Every file under `modules/**/*` starts with the same header, no blank lines before it. The guard placement differs by file type:

**Module Makefile** (`modules/<module>/Makefile`) — include the root *first*, then guard (the guard verifies the root actually loaded, since `-include` is silent on missing files):

```
#
# Filename: modules/<module>/Makefile
# Last edited: <YYYY-MM-DD> <HH:MM:SS>
# Description: <short summary>
#

-include .makefiles/modules/Makefile

ifndef MF_TOOLS_ROOT
$(error MF_TOOLS_ROOT is not set. Include modules/Makefile before using modules/<module>/Makefile.)
endif

<file content begins here>
```

**Helper fragment** (`modules/<module>/*.mk`) — guard only, no root include (the parent module Makefile loads the root before this file is included):

```
#
# Filename: modules/<module>/<file>.mk
# Last edited: <YYYY-MM-DD> <HH:MM:SS>
# Description: <short summary>
#

ifndef MF_TOOLS_ROOT
$(error MF_TOOLS_ROOT is not set. Include modules/Makefile before using <file>.mk.)
endif

<file content begins here>
```

**Root Makefile** (`modules/Makefile`) — header only, no guard (it is the file that *defines* `MF_TOOLS_ROOT`, so it cannot guard on it).

**Module shell helper** (`modules/<module>/*.sh`) — use this for module-specific
discovery logic (for example parsing project config files). Keep scripts
portable (`/usr/bin/env sh` unless Bash-only features are required) and add
them to `modules/manifest.txt`.

Checklist:
1. `Filename` uses the path relative to the repo root.
2. `Last edited` matches `date -r <file> +"%Y-%m-%d %H:%M:%S"` (local timezone).
3. `Description` is a one-liner (“Docker module targets for container tasks”).
4. Exactly one blank line separates the guard (or root include) from the rest of the file.

## 3. Include Rules

| File Type                                | Must include | Location of include | Notes |
|-----------------------------------------|---------------|----------------------|-------|
| `modules/Makefile` (root)               | _none_        | —                    | Already the root; no guard. |
| `modules/<module>/Makefile`             | `-include .makefiles/modules/Makefile` | Immediately after header, **before** the guard | Only once per file. |
| `modules/<module>/*.mk` helper files    | _never_       | —                    | Depends on parent Makefile; guard only. |
| `modules/<module>/*.sh` helper scripts  | _never_       | —                    | Standalone scripts; no Make include semantics. |

> Tip: keep all include paths literal (no variables) so downstream consumers can grep for them.

## 4. Adding a New Module

1. **Scaffold directories**
	```bash
	mkdir -p modules/<module>
	cp modules/Makefile modules/<module>/Makefile   # as reference
	```
2. **Configure `modules/<module>/Makefile`**
  - Include `.makefiles/modules/Makefile` immediately after the header, then add the guard.
  - Register `clean`, `install`, and `help`, plus every other public target.
  - Include `prerequisites.mk` and then `targets.mk` after the root include and guard.
3. **Create the required fragments**
  - Put prerequisite configuration and private prerequisite/support rules in `prerequisites.mk`.
  - Put public target declarations and recipes in `targets.mk`, using `::` for aggregate-contributing targets.
  - For reusable non-target snippets, create optional `.mk` helpers with the same header + guard but **without** including the root or defining targets.
  - For module-specific path/config discovery, prefer a module-local helper script (for example `discover-paths.sh`) over adding module-aware logic to core.
4. **Register in the manifest**
  - Add the module `Makefile`, `prerequisites.mk`, `targets.mk`, any `.mk` helpers, and module-local scripts to `modules/manifest.txt`, one path per line relative to `modules/`. Without this, `fetch` will not download the files.
5. **Update timestamps**
  - After editing, run `date -r modules/<module>/Makefile +"%Y-%m-%d %H:%M:%S"` and copy the result into the header.

## 6. Style & Safety Tips

- Keep recipes defensive: guard destructive commands with `if [ -d … ]` and quote paths.
- Use `$(MAKE)` when invoking other targets to preserve flags.
- Prefer double-colon (`target::`) when multiple files need to contribute to the same target.
- Avoid re-including the root from helper fragments; they inherit variables via the parent Makefile.
- Stay ASCII unless the file already uses Unicode (per repo policy).

## 7. Cache verification and updates

`fetch` records a `sha256sum -c`-compatible hash of every cached file in
`.makefiles/modules/.manifest.sha256` after each successful download, and the
module set carries a `VERSION` file (fetched like any other manifest entry).
Verification is local-only — a single `sha256sum -c` pass, no network — and
stays sub-second on the happy path.

When verification runs:

- `make <module> <target>` (scoped dispatch) verifies that module's recorded
  lines plus the shared root/core files before the recursive make.
- `make <target>` (aggregate mode, exactly one goal) verifies every imported
  module before the first goal's recipes run. `help` and `clean` are exempt:
  help is informational, and clean must always work offline as the escape
  hatch.
- The wtree module's `mf-wtree-ensure` verifies the wtree module's lines
  before invoking the binary, so direct `-f modules/wtree/Makefile` usage is
  protected too.

Self-heal semantics: on a hash mismatch or a missing record, the affected
module is re-fetched once with `--force` (via the published `fetch` script,
same pattern as the consumer bootstrap rule) and verified again. If the second
verification still fails, the build stops with an error naming the offending
file(s). There is no retry loop and no unbounded wait: every download is
bounded by `MAKEFILES_FETCH_MAX_TIME` (default 30 s) and
`MAKEFILES_FETCH_CONNECT_TIMEOUT` (default 10 s), both overridable via the
environment, as is the site root (`MAKEFILES_BASE_URL`, default
`https://darianbr.github.io/makefiles/modules`). A module that is absent from
the published manifest (a local-only module) is skipped by verification and
updates.

Version visibility and updates are explicit by design — a normal build never
re-fetches because the site is newer:

- `make modules-version` prints the recorded `VERSION` plus the first 12 hex
  characters of the cache record's hash, so two machines can be compared at a
  glance. Local-only; no network.
- `make modules-update` re-fetches every cached published module with
  `--force` and prints `<old> -> <new>`. It is never a prerequisite of any
  other target.

## 8. Pre-PR Checklist

From the repository root, run `make check` before submitting; it is also the
Makefile's default goal and is enforced by CI on every push and pull request.
`check-manifest` verifies that `modules/manifest.txt` exactly covers the files
under `modules/` (excluding the manifest itself), and `check-shell`
syntax-checks `fetch` with Bash and module helper scripts with POSIX `sh`.
These local checks require GNU Make, Bash, POSIX `sh`, and the standard
`find`, `sed`, `sort`, and `diff` utilities. They do not access the network or
run language-specific example workflows; run the relevant targets under
`examples/<module>/` separately for those.

Before submitting:

- [ ] Headers updated with accurate timestamps & descriptions.
- [ ] `MF_TOOLS_ROOT` guard present and correctly references the current filename.
- [ ] Module Makefiles include `-include .makefiles/modules/Makefile` directly after the header.
- [ ] Module Makefiles include `prerequisites.mk` then `targets.mk` after the root include and guard.
- [ ] Every module provides and registers `clean`, `install`, and `help`; no-op behavior is explicit where a target has no work.
- [ ] `prerequisites.mk` holds prerequisite configuration and private support rules; `targets.mk` contains public target definitions and recipes.
- [ ] Optional helper `.mk` files avoid extra includes and do not define targets.
- [ ] Every new/renamed file is listed in `modules/manifest.txt`.
- [ ] Verify `make <module> help` and `make <module> clean` in a safe example workspace; exercise `install` where appropriate.
- [ ] Documentation (README/CONTRIBUTIONS) updated if behavior is user-visible.
- [ ] Commits focus on a single module or cohesive change set.
- [ ] New published files are listed in `modules/manifest.txt` (covered by `make check-manifest`) and, if they are core infrastructure, added to the wtree module's `MF_WTREE_CORE_FILES` list.
